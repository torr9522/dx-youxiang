# Server migration

The stable identity is the mail hostname. A server migration restores accounts and data; it does not recreate mailboxes.

1. Install the pinned application and compatible Stalwart build on the new server.
2. Restore and validate the latest backup in isolation.
3. Schedule a short receive freeze, run a final backup on the old host, and restore it on the new host with `scripts/migrate-legacy.sh` when crossing the former project identity.
4. Verify account IDs, messages, attachments, folders, flags, passwords and permissions.
5. Verify the web UI, SMTP recipient validation, IMAP login switches, TLS and outbound firewall blocks.
6. Change the A record of the existing mail hostname to the new IPv4 address. Do not alter the MX record.
7. Keep the old server intact and firewalled for rollback until the DNS TTL and acceptance window have passed.

Rollback changes the A record back and restores the old listener rules. Mail received on the new host during the window must be exported and reconciled before rollback; DNS changes alone do not merge mail stores.

For an in-place `0.1.8` to `0.1.9` application migration, the application startup transaction creates one system-default `dx` mailbox group and fills only missing `mailboxes.group_id` values. Re-running startup is idempotent, including after the default group is renamed. The migration does not recreate Stalwart accounts or modify mailbox IDs, account IDs, addresses, permissions, messages, MIME, flags, folders or attachments. Verify those values against the pre-upgrade manifest and verify that no mailbox has a null or invalid group reference.

The migration deliberately does not restore old path-based systemd, Caddy, TLS or application configuration over the new installation. Those paths are generated by the pinned installer. Only the consistent Stalwart export, application SQLite data, administrator password hash and imported account credentials are migrated; the backend service credential and session secret are rotated.
